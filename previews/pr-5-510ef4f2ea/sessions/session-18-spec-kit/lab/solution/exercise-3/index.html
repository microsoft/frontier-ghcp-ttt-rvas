    Exercise 3 Solution¶

    This solution covers governance and risk management for specification-driven development.

    Structure¶

    • SETUP_GUIDE.md — Pinned-version installation
    • uv.lock — Locked dependencies (committed to repo)
    • governance/ — Enterprise policies
    • .specify/ — Specification and exclusion patterns
    • test-fallback/ — Fallback workflow simulation

    Part A: Version Pinning¶

    Risk¶

    # Unpinned version (risky for pre-1.0)
uv tool install specify-cli
# Could install different versions at different times (breaking changes)

# Team member A has version X, team member B has version Y
# Specifications diverge; CI fails unexpectedly

    Approved approach¶

    # Use corporate catalog or lockfile for reproducible pinning
uv sync --locked

# All team members, all CI runs, use the same version from uv.lock

    Documentation¶

    See SETUP_GUIDE.md for:

    • Why pinning matters for pre-1.0 tools
    • The corporate catalog's approved version
    • How to update (test in staging first)
    • What to do when a security issue requires an emergency update

    Part B: Lock File¶

    Risk¶

    # Dependencies are transitive trees
specify-cli depends on:
  - pydantic depends on:
    - typing-extensions>=4.8
    - pydantic-core depends on:
      - ...
# If you don't lock, each dev might get different sub-versions

    Approved approach¶

    # Generate lock file (one-time)
uv sync --locked

# Result: uv.lock contains exact versions of everything
# Commit to repo
git add uv.lock
git commit -m "Lock dependencies for reproducibility"

# Next time any team member runs:
uv sync --locked
# They get exact same versions (from lock file, not latest)

    Part C: Fallback Workflow¶

    Risk¶

    # What if Copilot is unavailable?
# - Model provider outage
# - Quota exhausted
# - Network down

# Without fallback, the whole specification workflow breaks

    Manual fallback¶

    # Initialize WITHOUT Copilot
specify init my-project --integration none

# Use templates from .github/skills/
ls -la .github/skills/specification-template/

# Fill in each phase manually (slower but functional)
cat > .specify/specification.yml << 'EOF'
# Manual specification (not generated by Copilot)
endpoints:
  - path: /api/v1/resource
    method: GET
    description: "Retrieve a resource"
    ...
EOF

# Continue with clarify, plan, checklist, tasks phases
# Take 2–3x longer, but doesn't require Copilot

# Result: Complete specification, just slower

    When to use fallback¶

    1. Copilot unavailable — Use the manual workflow for that day's work.
    2. Quota exhausted — Wait for reset or use the fallback.
    3. Network restricted — In an air-gapped environment, use cached skills and the manual workflow.
    4. Learning — The manual workflow teaches the phases in more depth.

    Part D: Content Exclusion¶

    Risk¶

    # Sensitive files should never be shown to AI models
.env         # Credentials
secrets.yml  # API keys
private-keys/  # SSH keys

# If these are in the repo and Copilot reads them, security risk

    Approved approach¶

    # .specify/exclusions.yml
sensitive_patterns:
  - "**/.env*"       # Environment variables
  - "**/secrets/**"  # Credential vault
  - "**/*.key"       # Private keys
  - "**/*.pem"       # Certificates
  - "config/credentials.yml"

# When Copilot reads the specification:
# 1. Specification context is loaded
# 2. Excluded patterns are filtered out
# 3. Copilot never sees sensitive files

# Verify exclusion works
specify check . --respect-exclusions --against .specify/specification.yml
# Output: ✓ N sensitive files hidden from Copilot

    Part E: Team Governance Policy¶

    See governance/specification-governance-policy.md for the policy template. It includes:

    Version Management¶

    • Pinned tool version: use corporate catalog/lockfile value (not hard-coded)
    • Lock file: uv.lock (required in every project)
    • Update process: Test in staging before a team rollout
    • Incident response: If security issue, follow emergency update procedure

    Copilot Integration¶

    • Primary model: Claude Sonnet 4.5 (approved by security)
    • Fallback model: GPT-4 Turbo (if primary unavailable)
    • Offline mode: Manual workflow (slower and without Copilot)
    • Cost tracking: Estimate AI credit use per specification

    Content Exclusion¶

    • Environment variables: always excluded
    • Credential files: always excluded
    • Sensitive database migrations: excluded + manual review
    • Audit: Quarterly review of exclusion list

    Team Responsibilities¶

    • Dev lead: Maintain pinned versions and lock files; update the pre-test plan
    • Security: Review new skills for credential exposure
    • Ops: Monitor Copilot API availability; activate the fallback when needed

    Review Cadence¶

    • Monthly: Check for security updates in specify-cli and dependencies
    • Quarterly: Evaluate new Copilot models and capabilities
    • As-needed: Respond to Copilot outages or API changes

    Running the Solution¶

    # 1. Verify pinned setup
cat SETUP_GUIDE.md

# 2. Check lock file
ls -la uv.lock
git log --oneline uv.lock | head -3

# 3. Test fallback workflow
cd test-fallback/
specify init manual-spec --integration none
# ... manually fill in phases ...
specify lint manual-spec/

# 4. Review content exclusion
cat .specify/exclusions.yml

# 5. Read governance policy
cat governance/specification-governance-policy.md

    Why this solution is enterprise-ready¶

    1. Reproducibility — Lock files give every team member the same setup.
    2. Resilience — The fallback workflow keeps Copilot unavailability from blocking work.
    3. Security — Content exclusion keeps credentials out of context.
    4. Governance — Policies state who makes each decision.
    5. Audibility — Decisions are documented and can be reviewed.

    Bring This Back to Your Team¶

    1. Pin your tools now. Do not wait for a breaking change.
    2. Generate lock files. Commit them to the repository.
    3. Document the fallback. Define what happens when Copilot is unavailable.
    4. Exclude sensitive data. Make exclusion automatic.
    5. Review quarterly. Update governance as the team grows.

    Security Checklist¶

    Before rolling out specification-driven development to your team:

    • Reviewed content exclusion patterns
    • Tested that sensitive files are hidden from Copilot
    • Documented who has access to governance policies
    • Planned incident response (Copilot outage, security issue)
    • Trained team on pinned versions and lock files
    • Set up quarterly governance review
